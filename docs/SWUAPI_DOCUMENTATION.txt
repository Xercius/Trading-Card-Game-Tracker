Star Wars: Unlimited – API Specification
=========================================

Document scope
--------------
This file records the base URL, authentication method, rate-limit behaviour,
known endpoints, and the real-world limitations/gotchas currently accounted for
by the Star Wars: Unlimited importer. It is based on the live-response shape
captured in repository tests, the importer/client implementation
(api/Importing/SwuDbImporter.cs, api/Importing/SWUApiClient.cs), the SWU
connectivity smoke test (api/scripts/test-swu-api-connectivity.sh), and the
existing reference notes in docs/starwarsunlimitedapi.txt.

IMPORTANT: The endpoints below are internal endpoints operated by Atomic Mass
Games / Fantasy Flight Games for the official card database at
https://starwarsunlimited.com. They are NOT a formally published public API.
They are based on Strapi and may change without notice.


1. BASE URL
-----------
https://admin.starwarsunlimited.com/api/


2. AUTHENTICATION
-----------------
Method  : Read-only HTTP GET requests. The current importer sends no auth.
Headers : The live importer sends only the standard headers added
          automatically by .NET's HttpClient.
Notes   : In repository-tested flows, card-list reads are attempted
          anonymously first. However, this endpoint is internal and upstream
          auth expectations may change without notice.

Gotcha  : The connectivity smoke test supports optional
          SWU_API_IDENTIFIER + SWU_API_PASSWORD or SWU_API_TOKEN inputs even
          though the importer itself does not send credentials.
Workaround:
          - Treat anonymous access as an observed convenience, not a stable
            contract.
          - If anonymous requests start failing, use
            api/scripts/test-swu-api-connectivity.sh to determine whether the
            endpoint now requires auth before changing importer behavior.
          - Write operations (POST/PUT/DELETE) are not consumed by this
            application and should not be assumed available to external users.


3. RATE LIMITING
----------------
Official limits : None have been publicly documented by the operator.
Observed limits : No explicit rate-limit response (HTTP 429) has been
                  encountered during normal import operations.
Practical rules applied by the importer/client:
  - HTTP client timeout : 5 minutes per request
  - Page size cap       : 100 records per page
  - Request shape       : Requests are paged sequentially
  - Automatic retry     : HTTP 429 only, up to 3 retries
  - Retry delay         : Retry-After header when present; otherwise 1 s,
                          2 s, then 4 s exponential back-off
Gotcha          : HTTP 503 and other non-success statuses are NOT retried by
                  the current client; they surface immediately as
                  HttpRequestException.
Recommendation  : Keep page size at or below 100, avoid concurrent fetches to
                  this host, and re-run the import later if upstream returns
                  503/5xx responses.


4. ENDPOINTS
------------
All endpoints are relative to the base URL above.
HTTP method for all consumer-accessible endpoints: GET

4.1  card-list
    Full path  : GET https://admin.starwarsunlimited.com/api/card-list
    Purpose    : Returns a paged list of card records (Strapi content-type).
    Used by    : SwuDbImporter.ImportFromRemoteAsync

    Required parameters : none (a bare GET returns all records)
    Common parameters (Strapi-style URL query string):

    Parameter                              Example value      Purpose
    -------------------------------------  -----------------  --------------------------------
    locale                                 en                 Language of returned records
    pagination[page]                       1                  1-based page index
    pagination[pageSize]                   100                Records per page (max ~100)
    sort[0]                                updatedAt:asc      Primary sort (importer default)
    sort[1]                                cardNumber:asc     Secondary sort
    sort[2]                                id:asc             Unique record tie-breaker
    filters[expansion][code][$eq]          SOR                Filter by expansion code
    filters[expansion][id][$eq]            2                  Filter by expansion internal ID
    filters[type][id][$eq]                 4                  Filter by card-type internal ID
    filters[variantTypes][id][$eq]         46                 Filter by variant-type internal ID
    filters[variantOf][id][$null]          true               Base cards only (no variants)
    filters[variantOf][id][$notNull]       true               Variant cards only
    filters[variantOf][id][$eq]            5                  Variants of a specific card ID
    filters[reprintOf][id][$eq]            12345              Reprints of a specific card ID
    filters[cardUid][$eq]                  1020365882         Lookup by public card UID
    filters[createdAt][$gte]               2025-08-01T00:00:00.000Z  Created on/after date
    filters[updatedAt][$gt]               2026-06-01T00:00:00.000Z  Updated after date

    Catalog identity and mapping evidence (normalized importer)
        The captured example in starwarsunlimitedapi.txt has record id 39380,
        cardUid "1020365882", and serialCode "06010001". Every printing has its
        own distinct cardUid and Strapi id, while logical cards are identified
        by `(Title, Subtitle)` (`Card.Name`). All printings of a card (Standard,
        Foil, Hyperspace, Showcase, Promo, Reprints) share a single `Card` row
        and create distinct `CardPrinting` rows.

        Expansion `publishedAt` (or synthetic `releaseDate`) is mapped to
        `Sets.ReleasedAt`. Aspect `color` is mapped to `Aspects.Color`, and
        rarity `character` and `color` are mapped to `Rarities.Character` and
        `Rarities.Color`.

    Response shape:
    {
      "data": [
        {
          "id": <integer>,            // internal Strapi record ID
          "attributes": {
            "title":       <string>,
            "subtitle":    <string|null>,
            "cardUid":     <string>,  // public card printing identifier (CID)
            "serialCode":  <string|null>, // set/card/variant identifier
            "locale":      <string>,  // e.g. "en"
            "cardNumber":  <integer>,
            "rarity":      { "data": { "id": <int>, "attributes": { "name": <string>, "character": <string>, "color": <string> } } } | null,
            "text":        <string|null>,
            "artist":      <string|null>,
            "cost":        <integer|null>,
            "power":       <integer|null>,
            "health":      <integer|null>,
            "arena":       <string|null>,
            "aspects":     { "data": [{ "id": <int>, "attributes": { "name": <string>, "color": <string> } }] },
            "traits":      { "data": [{ "id": <int>, "attributes": { "name": <string> } }] },
            "keywords":    { "data": [{ "id": <int>, "attributes": { "name": <string> } }] },
            "updatedAt":   <ISO-8601 timestamp>,
            "createdAt":   <ISO-8601 timestamp>,
            "publishedAt": <ISO-8601 timestamp>,
            "type": {
              "data": { "id": <int>, "attributes": { "name": <string>, "value": <string> } }
            },
            "expansion": {
              "data": { "id": <int>, "attributes": { "name": <string>, "code": <string>, "publishedAt": <ISO-8601 timestamp> } }
            },
            "variantTypes": {
              "data": [
                { "id": <int>, "attributes": { "name": <string>, "variantId": <string>, "foil": <bool> } }
              ]
            },
            "variantOf":  { "data": { "id": <int>, "attributes": { "title": <string>, "cardUid": <string> } } | null },
            "reprintOf":  { "data": { "id": <int>, "attributes": { "title": <string>, "cardUid": <string> } } | null },
            "artFront": {
              "data": {
                "id": <int>,
                "attributes": {
                  "url": <string>,
                  "formats": {
                    "card":      { "url": <string> },
                    "thumbnail": { "url": <string> },
                    "xsmall":    { "url": <string> },
                    "xxsmall":   { "url": <string> },
                    "xxxsmall":  { "url": <string> }
                  }
                }
              }
            },
            "artBack": { "data": { "id": <int>, "attributes": { "url": <string> } } | null }
          }
        }
      ],
      "meta": {
        "pagination": {
          "page":      <integer>,
          "pageSize":  <integer>,
          "pageCount": <integer>,
          "total":     <integer>
        }
      }
    }

    Pagination: iterate page=1..pageCount (inclusive) to retrieve all records.
    Aspects, traits, and keywords are Strapi relationships (verified live).
    Empty relationships use "data": []; optional fields may also be null.
    Legacy string arrays in imported files are still accepted.
    Rarity is a single Strapi relationship; its data.attributes.name is
    normalized to a string (e.g. "Special", "Common", "Rare", "Legendary")
    while preserving character and color metadata for lookup tables.
    Legacy string rarity values remain supported. Missing/null rarity or
    null relationship data/name retains the existing "Unknown" fallback.

4.2  No other endpoints are currently used by this application.
    The Strapi framework underlying the site likely exposes additional
    content-type endpoints (e.g. /api/expansions, /api/card-types), but they
    have not been verified and are not consumed by any importer in this
    codebase. Any future use of additional endpoints should be documented in
    a new section here before being relied upon in production code.

    Gotcha: there is no repository-verified dedicated "list all sets" endpoint
    that this application depends on.
    Workaround: derive expansion metadata from `card-list` itself:
      - set code  : data[].attributes.expansion.data.attributes.code
      - set name  : data[].attributes.expansion.data.attributes.name
      - set ID    : data[].attributes.expansion.data.id

6. FILTER OPERATOR REFERENCE
------------------------------
Operator      Meaning
-----------   -------------------------------------------
$eq           Equal
$ne           Not equal
$eqi          Equal, case-insensitive
$in           Included in a list
$notIn        Not included in a list
$gt           Greater than
$gte          Greater than or equal
$lt           Less than
$lte          Less than or equal
$contains     Contains substring
$containsi    Contains substring, case-insensitive
$null         Is null (value: true)
$notNull      Is not null (value: true)
$and          All child conditions must match
$or           At least one child condition must match
$not          Negates a condition

Caveat: this is a customised Strapi endpoint. Not every operator is
guaranteed to work for every relational field. Negative filters on
many-to-many relations ($notIn, $ne) can produce unexpected results;
prefer client-side exclusion for those cases.


7. TIMESTAMP METADATA AND UPDATE DETECTION  (Task 2.4 findings)
--------------------------------------------------------------

7.1  Timestamp fields returned by the API
    Every card record in the `attributes` object contains three timestamp
    fields managed automatically by Strapi:

    Field         Type                    Notes
    ------------  ----------------------  ----------------------------------
    createdAt     ISO-8601 UTC string     Set once when the record is first
                                          published; never changes afterwards.
    updatedAt     ISO-8601 UTC string     Bumped by Strapi every time any
                                          attribute on the record is changed.
                                          This is the authoritative field for
                                          detecting modifications.
    publishedAt   ISO-8601 UTC string     Set when the record is published;
                                          may equal createdAt for cards that
                                          go live immediately.

    Example values observed in production data:
      "createdAt":   "2025-08-15T18:29:41.633Z"
      "updatedAt":   "2025-11-10T16:07:21.320Z"
      "publishedAt": "2025-08-15T18:30:00.000Z"

7.2  Date format
    All three fields use ISO 8601 / RFC 3339 format with millisecond
    precision and a literal 'Z' UTC suffix:

      yyyy-MM-ddTHH:mm:ss.sssZ

    When constructing filter query parameters, use the same format:

      filters[updatedAt][$gt]=2025-11-01T00:00:00.000Z

    The C# importer represents these values as `DateTimeOffset?` and
    serialises them back to the same format via `System.Text.Json`.

7.3  Date filtering support
    Date filtering IS supported via the standard Strapi filter syntax.
    Tested operators for timestamp fields:

    Operator   Example                                         Notes
    ---------  ----------------------------------------------  -------------------
    $gt        filters[updatedAt][$gt]=2025-11-01T00:00:00.000Z  strictly after
    $gte       filters[createdAt][$gte]=2025-08-01T00:00:00.000Z on/after date
    $lt        filters[updatedAt][$lt]=2026-01-01T00:00:00.000Z  strictly before
    $lte       filters[createdAt][$lte]=2025-12-31T23:59:59.000Z on/before date

    Combine with other filters using the standard Strapi AND behaviour:

      filters[expansion][code][$eq]=SOR&filters[updatedAt][$gt]=2025-11-01T00:00:00.000Z

7.4  Reliable strategy to detect new/updated cards
    Recommended approach for incremental synchronisation:

    1.  Record the UTC timestamp immediately before each successful import
        run (e.g. `DateTimeOffset.UtcNow` captured at start of run).

    2.  Persist that start timestamp only after a complete, error-free
        unlimited remote import commits. Dry-runs, file imports, limited
        imports, and partially failed imports must not advance coverage.
        On the next run supply the checkpoint with overlap as `UpdatedSince` in
        `ImportOptions`.  The importer will add
        `filters[updatedAt][$gt]=<timestamp>` to every API request, so
        only records modified since the previous run are fetched.

    3.  Sort results by `updatedAt:asc` (the importer default).
        Page-number pagination is not a snapshot when upstream data changes.
        Do not advance a timestamp cursor after a partially processed run;
        retry from the previous successful checkpoint.

    4.  Apply a small overlap (subtract ≥ 1 minute from the stored
        timestamp) to guard against sub-second clock skew and records
        whose `updatedAt` falls exactly on the boundary.

    5.  The shared SWU importer's upsert logic is idempotent:
        re-importing a card that has not changed produces no DB writes
        (no `CardsUpdated` / `PrintingsUpdated` increments), so
        overlapping records are safe to re-fetch.

    6.  Prefer `updatedAt` over `createdAt` as the synchronisation field
        because it catches both newly added cards and corrections to
        existing cards (text, artwork, rarity, etc.).

    Full-catalog fallback: the admin sync panel omits `UpdatedSince` when no
    global checkpoint is available, or during full reconciliation, and imports
    the unfiltered catalog. A direct import may instead specify one expansion.
    The importer's upsert behaviour ensures idempotency.

    The admin sync panel automatically applies a one-minute overlap and
    offers Full reconciliation (?forceFullSync=true). Use full reconciliation
    periodically and once after upgrading from older unsafe checkpoint logic.
    See docs/SWU_IMPORT_GUIDE.md for the current wiring and compatibility policy.

    C# `ImportOptions` parameter: `UpdatedSince` (type `DateTimeOffset?`).
    When set, the importer emits `filters[updatedAt][$gt]=...` in the
    query string automatically.


8. LOCALIZATION BEHAVIOUR
-------------------------
The `locale=en` query parameter selects English as the top-level locale,
but English card records may still contain nested relationship data for
other languages.

Example of a nested localisation reference inside an English record:

    "localizations": {
      "data": [
        { "attributes": { "locale": "it" } }
      ]
    }

This does NOT indicate the returned card is Italian – it means the English
record links to its Italian translation.

To determine the language of a card record, always inspect:

    data[].attributes.locale

Do NOT infer language from the nested `attributes.localizations.data` list.
The importer sets `locale=en` and skips any additional population of
`localizations`, so the top-level `attributes.locale` will always be "en"
for records returned by the importer.


9. IMAGE URL RESOLUTION
-----------------------
Image data is returned under two Strapi media relationships:

  artFront  – front card art (primary image)
  artBack   – back card art (dual-sided cards only; may be null)

Each media relationship contains an original URL and a set of pre-scaled
format URLs inside the `formats` object.

Response structure example (artFront):

    "artFront": {
      "data": {
        "id": <int>,
        "attributes": {
          "url": "<original high-resolution URL>",
          "formats": {
            "card":      { "url": "<~card-sized URL>" },
            "thumbnail": { "url": "<~thumbnail URL>" },
            "xsmall":    { "url": "<~xsmall URL>" },
            "xxsmall":   { "url": "<~xxsmall URL>" },
            "xxxsmall":  { "url": "<~xxxsmall URL>" }
          }
        }
      }
    }

Not every format key is guaranteed to be present for every card. The
`artBack` relationship follows the same structure but `formats` may be
absent or empty.

Shared importer image priority:

  1. artFront.data.attributes.url         (original resolution)
  2. artFront.data.attributes.formats.card.url
  3. artFront.data.attributes.formats.thumbnail.url
  4. artBack.data.attributes.url          (fallback for dual-sided cards)

Note: The importer C# model (SwuImageFormats) only deserialises the
`card` and `thumbnail` format keys. The `xsmall`, `xxsmall`, and
`xxxsmall` keys exist in the API response but are not consumed; add them
to SwuImageFormats if finer-grained image resolution is needed.


10. VARIANT AND REPRINT EXCLUSION
-----------------------------------
Many-to-many relational fields (e.g. `variantTypes`) cannot be reliably
excluded using simple $ne/$notIn URL filters in this custom Strapi
endpoint. A card that belongs to multiple variant types can still satisfy
a "not equal" condition through a different related record.

For example, a card with variantTypes = [46, 51] will match
`filters[variantTypes][id][$ne]=46` because it also relates to ID 51.

Recommended approach for exclusion:

  1. Retrieve all records for the expansion without any exclusion filter.
  2. In your application code, inspect `variantTypes.data` for each card.
  3. Discard any card whose `variantTypes.data` contains an ID in the
     exclusion set.

Example exclusion logic (JavaScript):

    const excluded = new Set([46, 51, 56, 61, 66, 81, 86, 91]);
    const baseCards = cards.filter(c => {
      const ids = c.attributes.variantTypes?.data?.map(v => v.id) ?? [];
      return !ids.some(id => excluded.has(id));
    });

The importer does not currently apply exclusion filters; it imports all
records returned for the specified expansion code.


11. TROUBLESHOOTING
-------------------
Problem: Date filter returns no results
  Cause  : Timestamp must use the exact format yyyy-MM-ddTHH:mm:ss.sssZ
            (milliseconds + literal Z). Omitting milliseconds may fail.
  Fix    : Use filters[updatedAt][$gt]=2025-11-01T00:00:00.000Z

Problem: Filtering reprintOf by cardUid returns nothing
  Cause  : filters[reprintOf][id][$eq] expects the internal numeric
            record ID, not the public cardUid / CID.
  Fix    : First resolve the CID:
             GET card-list?filters[cardUid][$eq]=<CID>&pagination[pageSize]=1
           Then use the returned top-level `id` in:
             filters[reprintOf][id][$eq]=<INTERNAL_ID>

Problem: $notIn does not exclude many-to-many relation IDs
  Cause  : Described in section 10 above.
  Fix    : Retrieve the full dataset and filter client-side.

Problem: Response contains records in languages other than English
  Cause  : Nested `localizations` relations are included in English
           records (see section 8).
  Fix    : Check data[].attributes.locale == "en". Nested localisation
           objects do not affect the top-level card language.

Problem: Empty response after adding filters
  Fix    : Remove filters one at a time to identify the offending filter:
           1. Test with only locale and pagination parameters.
           2. Add the expansion filter.
           3. Add the type filter.
           4. Add variant/reprint filters last.

13. VERIFIED LIMITATIONS, GOTCHAS, AND WORKAROUNDS
--------------------------------------------------
These are the behaviors the current repository explicitly accounts for in the
importer, tests, or smoke-test tooling.

13.1  Internal, unstable upstream API
      Limitation: `card-list` is an internal Strapi endpoint, not a supported
      public contract.
      Workaround: keep this file, `docs/SWU_IMPORT_GUIDE.md`, and
      `api/scripts/test-swu-api-connectivity.sh` in sync whenever the payload
      shape changes.

13.2  Single-expansion imports are caller-driven
      Limitation: direct single-expansion imports require a set code up front.
      The admin sync workflow does not: it imports the unfiltered catalog and
      discovers new expansions from the card records.
      Workaround: use the global admin sync for catalog coverage. For a
      single-expansion import, supply its code and let the importer resolve
      the numeric Strapi ID dynamically when possible.

13.3  Numeric expansion ID lookup is best-effort
      Gotcha: for a direct single-expansion import, the importer first tries
      `filters[expansion][code][$eq]=<CODE>` with `pagination[pageSize]=1` to
      discover the internal expansion ID. If that request fails or returns no
      cards, the import falls back to the code filter. Global admin sync does
      not resolve or filter by expansion.
      Workaround: prefer `filters[expansion][id][$eq]` once you know the ID;
      treat code-based filtering as a fallback for single-expansion imports.

13.4  English-only import is enforced twice
      Gotcha: requests always include `locale=en`, but the importer still checks
      `data[].attributes.locale` and skips non-English records.
      Workaround: do not rely only on the URL parameter; validate the top-level
      record locale, especially when replaying captured files.

13.5  File imports are more permissive than the live API contract
      Gotcha: `ImportFromFileAsync` accepts either the full Strapi envelope
      (`{ "data": [...], "meta": ... }`) or a bare array for backwards
      compatibility. The remote API contract remains the Strapi envelope.
      Workaround: use enveloped payloads for captures/documentation; reserve
      bare arrays for deterministic local test fixtures only.

13.6  Missing fields fall back to synthetic values
      Gotcha:
        - missing `serialCode`  -> printing key falls back to `set + cardNumber`
        - missing `cardNumber`  -> printing number falls back to top-level `id`
        - missing `expansion`   -> set falls back to `UNK`
      Workaround: expect stable upserts only when `serialCode` or
      `expansion+cardNumber` are present; audit any `UNK` set values after an
      import because they indicate incomplete upstream data.

13.7  Base-card linking requires the referenced upstream record
      `variantOf` / `reprintOf` metadata is retained. Deferred relationship
      resolution uses upstream identifiers, not display titles, and excludes
      self-links. Import order within a payload does not determine linkage.
      If the base belongs to an absent set, import that set; unresolved
      references are retained for subsequent relationship repair.

13.8  Incremental sync must overlap the boundary
      Gotcha: update detection uses strict `filters[updatedAt][$gt]=...`.
      Records whose timestamps land exactly on the saved boundary can be missed
      if you reuse the previous timestamp verbatim.
      Workaround: subtract at least one minute from the stored sync time before
      the next incremental run. The importer upsert path is idempotent, so
      re-fetching a small overlap is safe.

13.9  Variant-type exclusion is not trustworthy server-side
      Limitation: `$ne` / `$notIn` filters on `variantTypes` can still match a
      record through a different related row in this customized Strapi
      endpoint.
      Workaround: fetch the broader result set, inspect
      `variantTypes.data[*].id`, and exclude unwanted variant IDs client-side.
